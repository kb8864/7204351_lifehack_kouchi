## 0. 一言サマリー（お忙しい方向け）

- 今のアプリは **Vercel という無料サービスの“借りた住所”（`729summerlifehacks.vercel.app`）** で動いています。
- このまま別のサーバー（AWS）へ引っ越すと、**利用者の「お気に入り」が消えてしまいます。**
- そこで、**先に自分たちの「独自ドメイン（自分の住所）」を取得し、今のうちから使い始める**ことで、後でサーバーを引っ越しても**お気に入りが消えない**状態を作ります。
- 利用者の使い勝手・表示速度は**ほぼ変わりません**。
- 費用は **独自ドメイン代（年 約1,500円）が中心**で、サーバー代は当面ほぼ無料の見込みです（詳細は別紙「予想予算書」）。

> 👉 **今回お願いしたいご承認**: ①独自ドメインの取得、②それを今のアプリに接続して運用開始、の2点です。AWSへの引っ越し自体は、準備が整ってから改めてご相談します。

## 2. 利用者への影響（ほぼありません）

- **表示速度**: ほぼ変わりません。一覧やトップは事前生成＋CDN配信で高速、という今の仕組みを引き継ぎます。
- **操作**: お気に入り・検索・投稿フォームなど、使い方は一切変わりません。
- **唯一の差**: 「長期間（数週間以上）誰も使わなかった後の“最初の1回”」だけ、表示が少し遅くなる可能性があります（無料データベースの休眠仕様のため）。夏の活動期のように普通に使っていれば発生しません。
- アドレス（URL）は独自ドメインに変わるため、**周知（新URLの案内）が一度だけ必要**です。

---

## 3. なぜ「独自ドメインが先」なのか（お気に入りの仕組み）

お気に入りは、利用者のスマホのブラウザに保存される**小さな合言葉（Cookie：`shichifuku_uid`）**と、サーバー側のデータを結びつけて成り立っています。

- この合言葉は **「アドレス（ドメイン）ごと」に保存** されます。
- そのため、**アドレスが変わると合言葉が一致しなくなり、お気に入りが“ゼロ件”に見えてしまいます**（データ自体は残っていても、本人と結びつけられない）。
- サーバーの引っ越し（Vercel→AWS）では、**アドレスを独自ドメインのまま変えなければ、合言葉は維持され、お気に入りも保持されます。**

> ✅ つまり「**独自ドメインを先に用意 → そのドメインで運用開始 → 後でサーバーだけ引っ越す**」とすれば、お気に入りは守られます。

> ⚠️ **正直な注意**: 今 `vercel.app` のアドレスに貯まっている**既存のお気に入りは、独自ドメインへ切り替えた“その瞬間”に引き継げません**（ブラウザの仕様上、別アドレスの合言葉は共有不可）。
> → **対策: できるだけ早い段階で独自ドメインに切り替える**ことで、失う件数を最小化します（利用が本格化する前ほど影響が小さい）。

## 5. 具体的な実装手順（担当者向け）

### フェーズ① 独自ドメイン取得
1. レジストラ（お名前.com / Google Domains後継 / Cloudflare Registrar 等）で独自ドメインを取得（年 約1,500円〜）。
2. DNS管理は **レジストラ標準 / Cloudflare（無料）/ AWS Route 53（月約80円）** のいずれでも可。※Route 53は必須ではない。

### フェーズ② 独自ドメインを“今のVercel”へ接続
1. Vercel の対象プロジェクト → **Settings → Domains** に独自ドメインを追加。
2. 指示される DNS レコード（A または CNAME）を DNS 管理画面に登録。SSL証明書はVercelが自動発行。
3. アプリ側の設定を独自ドメインに更新:
   - 環境変数 `NEXT_PUBLIC_APP_URL` を新URLに変更（Vercelの環境変数）。
   - **Googleフォーム連携（GAS）**: `app/scripts/google-apps-script.js` の `WEBHOOK_URL` を新URLに変更し、**フォームのスクリプトエディタへ貼り替え**（GASは手動反映が必要）。
   - **LINEログインを使う場合**: LINE Developersコンソールのコールバック（リダイレクト）URIを新URLに更新。
4. 新URLで一通り動作確認 → 利用者へ新URLを周知。

### フェーズ③ AWS事前検証（着手前ゲート）
- ⚠️ 本アプリは **Next.js 16.2.6（最新・特殊構成）**。AWS Amplify が Next.js 16 のサーバー機能（SSR/ISR/ミドルウェア）に対応しているかを**先に検証**する。
- 未対応の場合の代替（いずれも **Supabaseは据え置き**で費用感は同等）:
  - **OpenNext / SST**（AWS Lambda + CloudFront 構成）
  - **AWS App Runner**（コンテナで常駐。月+10ドル程度）
  - **Vercel継続**（独自ドメインのみ。AWSに拘らない場合の最小リスク）

### フェーズ④ サーバー引っ越し（Amplify）
1. AWS Amplify Hosting に GitHub リポジトリを接続。
2. **モノレポ設定**: アプリ本体は `app/` 配下だが、データJSON（`../public/*.json`）を参照するため、**リポジトリ全体を取得し、ビルド/実行の作業ディレクトリを `app/` に設定**する（`app/public/images/*` は静的配信）。
3. 環境変数を Amplify に登録（下表）。`NEXT_PUBLIC_APP_URL` は独自ドメイン。
4. Amplify で発行されるURLで動作確認後、**DNSの向き先を Vercel → Amplify に変更**（事前にDNSのTTLを短くしておく）。**ドメインは不変**。
5. 問題があれば **DNSをVercelに戻すだけでロールバック**可能。

#### 設定が必要な環境変数（全8項目）
| 変数名 | 種別 | 用途 |
|---|---|---|
| `NEXT_PUBLIC_SUPABASE_URL` | 公開 | Supabase接続先 |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | 公開 | Supabase公開キー |
| `SUPABASE_SERVICE_ROLE_KEY` | **機密** | サーバー用Supabaseキー |
| `WEBHOOK_SECRET` | **機密** | Googleフォーム連携の認証 |
| `JWT_SECRET` | **機密** | 管理者ログインの署名鍵 |
| `ADMIN_USERNAME` | **機密** | 管理者ユーザー名 |
| `ADMIN_PASSWORD` | **機密** | 管理者パスワード |
| `NEXT_PUBLIC_APP_URL` | 公開 | アプリの公開URL（独自ドメイン） |

> 機密はAWS **Secrets Manager / SSM Parameter Store** での管理を推奨（任意）。

### フェーズ⑤ お気に入り保持の検証（重要）
1. 独自ドメイン接続後、検証端末でライフハックを1件お気に入り → ブラウザの合言葉 `shichifuku_uid` の値を控える。
2. Amplify切替後、**同じ端末・同じドメイン**で再訪し、お気に入りが残っていること／`shichifuku_uid` が同値であることを確認。
3. Supabase ダッシュボードで `anonymous_favorites` に該当の行があることを確認。
4. お気に入りの追加・解除、件数の反映、検索、投稿フォーム、管理画面ログインを一通り確認。

## 6. リスクと対策

| リスク | 影響 | 対策 |
|---|---|---|
| 既存お気に入りが切替時に引き継げない | 一部のお気に入りが消える | **早期に独自ドメイン化**して件数を最小化。橋渡しは複雑なため非推奨。 |
| Next.js 16 が Amplify 未対応 | 引っ越し方法の変更 | フェーズ③で**事前検証**。未対応ならOpenNext/App Runner/Vercel継続に切替。 |
| 無料Supabaseが7日休眠 | 長期未使用後の初回が遅い | 活動期は問題なし。常時即応が必要ならSupabase有料（月約3,900円）へ。 |
| DNS切替の不具合 | 一時的に表示不可 | TTL短縮＋段階切替。**向き先を戻すだけで即ロールバック**。 |
| GAS/LINEのURL未更新 | 投稿/ログイン不可 | チェックリストで更新漏れ防止（手順5に明記）。 |

## 7. 代替案 B（フルAWS：参考）

「データベースも含めて完全にAWSへ寄せたい」場合の案。

- 構成: AWS Amplify/Lambda ＋ **Amazon RDS（PostgreSQL, t4g.micro）**。Supabaseは使わない。
- お気に入り含む全データは `pg_dump`/`pg_restore` で RDS へ移行（AWS料金は不要、作業工数のみ）。
- 追加作業: アプリのデータ処理を Supabase用から PostgreSQL直結（pg/Prisma等）へ**書き換え**。
- 費用: 新規AWSアカウントなら最初の半年は無料枠でほぼ0円。無料枠終了後は**常時起動のデータベース代が中心**（詳細は予算書）。
- 判断: 今回の規模（最大150人・たまに利用）では **A案（Supabase据え置き）の方が安く・改修も少なく・お気に入りも無傷**のため、A案を推奨。B案は将来「完全AWS化したい」となった時の選択肢として保持。

## 付録: 用語ミニ解説（IT初心者向け）

- **ドメイン**: インターネット上の「住所」。`vercel.app` は借り物、独自ドメインは自分の持ち物。
- **ホスティング / サーバー**: アプリを動かして配信する場所。Vercel・AWSなどが提供。
- **Cookie（クッキー）**: ブラウザに保存される小さなメモ。本アプリでは「あなたを匿名で識別する合言葉」に使用（お気に入りの紐づけ）。
- **Supabase**: データ（ライフハック・お気に入り）を保存しているクラウドのデータベースサービス。
- **AWS Amplify**: AWSが提供する、Vercelに近い「アプリ配信サービス」。
- **DNS**: ドメイン（住所）を実際のサーバーに案内する仕組み。引っ越しは「案内先の変更」で行う。
